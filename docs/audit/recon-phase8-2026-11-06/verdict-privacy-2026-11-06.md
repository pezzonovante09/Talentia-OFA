# Вердикт приватности по фазе 8 ABA (`child-privacy-compliance`, 2026-11-06)

**Одной строкой:** блокеров нет; по всем пунктам «без блокера» при условиях ниже (условия — для проверки по
диффу). Правка `consentBody` / privacy-policy не требуется, вопрос юристу из фазы 8 не возникает.

## б) Ключ `abaSessionLeft: { sessionId; at } | null` — без блокера

Момент ухода — та же категория, что уже лежит локально в большем объёме (`startedAt`/`endedAt` сессии, события
`break`/`access`, `sdEndedAt` проб, `updated_at` снимка). Новой категории и получателя нет. Альтернатива через
`updated_at` приватно-эквивалентна — выбор за `backend-auditor`.

Условия:
1. Ключ в `ABA_STATE_KEYS` → автоматически в `ABA_DELETED_KEYS` и `abaIdleChildren`; миграция 17 пересоздаёт оба
   триггера `child_state_aba_need_consent_*` и `consent_events_aba_revoke_needs_purge` с ключом в списке.
2. `IN_PROGRESS_KEYS` расширить недостаточно: `applyRetention` (`purge.ts` 160–166) удаляет по
   `json_extract(body, '$.startedAt')`, а тело ключа `{ sessionId, at }` — нужен отдельный предикат (`'$.at'`) или
   правило «ключ без снимка — удалить».
3. В `SPECIALIST_STATE_KEYS` не добавлять. В `exportChild` (полный экспорт родителя) попадёт сам — верно.
4. `commitAbaSession` и `abandonInProgressSession` сбрасывают ключ в `null` той же транзакцией.

## г1) Отзыв согласия, пока свёрнуто — без блокера

Три заслона: `revokeAbaProcessing` удаляет журналы и `ABA_DELETED_KEYS` одной транзакцией; любая запись идёт через
`withAbaWrite` → `requireAbaConsent`; триггеры базы отклоняют вставку без `aba_write_gate`. Путь «из памяти в базу
после отзыва» не существует, если `aba_session_tails` и `abaSessionLeft` попали в триггеры миграции 17.

Условия: `classifyWriteError` → `'blocked'` и в `onLeave` (без повтора и без `console` вне `__DEV__`);
`loadAbaResume` при `'none'`/`'blocked'` не пытается обнулить `abaSessionLeft` (запись ключа ABA упадёт на триггере).

## г2) Пауза включена, пока свёрнуто — без блокера

Снимок содержит ровно те данные, что уже лежат в `aba_trials`, плюс конфигурацию и uuid наблюдателей. Срок снимка
уже ограничен `applyRetention` по `startedAt` и `abaIdleChildren` (12 мес). Отдельный срок не нужен.

Условие: после снятия паузы просроченный снимок уходит в `in_progress_stale` и закрывается действием родителя.
`abaDataSummary` снимок не считает — расхождения для «будет удалено N» нет.

## е3) Таблица `aba_session_tails` — без блокера, consentBody / privacy-policy не меняются

Категории: `accessScene` = событие `access`; `pairingTokenAt` = событие `pairing`; `leftAtStep` — ход процедуры
(как `endReason`, `assent.action`); `leftAt` — время, как у всех событий; `completed` — булево. Ничего сверх
записанного; получатель прежний. `consentBody` draft-2 и privacy-policy строка 38 («сессии») покрывают.

Условия:
1. Таблица — в `JOURNALS` (через него `wipeDevice`), `RETENTION_COLUMNS`, `revokeAbaProcessing`, триггер
   `revoke_needs_purge`, `gated` + `retained` + `need_consent` по образцу `aba_routine_run_amendments`.
2. `exportChild` включает `abaSessionTails` (право доступа родителя).
3. `exportForSpecialist`: времена только через `relativeTimes(tail, sessionStart.get(sessionId))`; хвост без записи
   сессии → даты `null`, как у осиротевших проб. Правило чтения методиста — в документ экспорта.
4. В хвост не пишется ничего кроме перечисленных полей: ни текст ошибки, ни `awayMs`, ни имя фазы экрана.

**Формулировка для ABA.md «Данные»** (абзац после «Хранение»):

> **Хвост конца занятия и прерывания.** Отдельный дописывающий журнал `aba_session_tails` — одна строка на сессию:
> фактические отрезки доступа к подкрепителю после итогового обмена (0–2), момент жетона цикла сопряжения, шаг
> хвоста, на котором занятие было прервано (`exchange` / `access` / `wait` / `pairing_token` / `null`), момент
> прерывания и признак «хвост доигран». Это ход процедуры, не данные о ребёнке сверх событий сессии; новых категорий
> и получателей не добавляет. Пишется только через `commit.ts` под воротами согласия, хранится 12 месяцев, удаляется
> при отзыве `aba_processing` вместе с журналами; родителю — в полном экспорте, специалисту — полем `tail` со
> смещениями от начала сессии (абсолютного времени и времени суток в файле нет). Момент сворачивания приложения во
> время занятия (`abaSessionLeft` в `child_state`) — служебный ключ ABA-состояния: под теми же воротами, удаляется
> при отзыве, сбрасывается при записи итога, по сроку — вместе со снимком; специалисту не экспортируется. Причины
> конца `app_backgrounded` (приложение свёрнуто дольше порога) и `app_error` (программная ошибка) — значения
> существующего поля `endReason`; сама ошибка (текст, стек) в журнал не попадает.

## Новые причины конца `app_backgrounded` и `app_error` — без блокера

Расширяется существующее перечисление, как в №164. Условие: в журнал и экспорт идёт только значение перечисления;
`e.message`/стек нигде не сохраняются.

## «Ни ошибки, ни имена ABA-экранов вне `__DEV__`» — без блокера, с условиями

Паттерн `if (__DEV__) console.warn(…)` соблюдён везде; требуется то же для всех новых точек (`useAbaBackground`,
`loadAbaResume`, `abandonInProgressSession`, `markAbaSessionLeft`, повторы при конфликте).

1. Ни один `async`-колбэк хука фона и старта не оставляет необработанный reject: в release единственный выход
   наружу — нативный крэш-репорт в статистике сторов, и туда попал бы текст JS-ошибки (сообщения `abaLog.ts`
   связывают устройство с режимом). `classifyWriteError` покрывает `onLeave` и `onReturn`; `'other'` без
   `st.current` — `endWithoutWrite()`, не `throw`.
2. Теги `console.warn` — только под `__DEV__`; в строках ru/en/ky для родителя не выносить слово «ошибка» с
   техническими деталями (зона `design-lead`).

## Вопросы юристу

Из фазы 8 — нет. При следующей редакции privacy-policy строку 38 можно дополнить «перерывы и прерывания занятия
(в том числе сворачивание приложения)» — уточнение существующей категории, не блокирует.

## Не моя зона

DDL миграции 17, идемпотентность, выбор «ключ против `updated_at`» — `backend-auditor`. Тексты карточки родителя
— `design-lead`. Data Safety / App Privacy (локально, без передачи — не меняются) — `release-readiness-auditor`, фаза 9.
