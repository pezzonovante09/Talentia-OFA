# Миграция Supabase

Производит одну миграцию и её проверки: файл в `supabase/migrations/`, тест в
`supabase/tests/`, зелёный `npm run test:db`. Схема касается данных детей, поэтому порядок
жёсткий: сначала спецификация агента зоны, потом SQL, потом тесты, потом проверка агентом.

## Перед началом

1. **Спецификация.** Если в задаче нет готового SQL или точного поведения — сначала агент:
   `child-privacy-compliance` для всего, что касается ребёнка, согласий, журналов и доступа;
   `backend-auditor` для схемы, индексов, функций. Решения, которых нет в задании, не
   принимать молча. Готовый SQL из отчёта агента (например, `docs/audit/round2-*.md`) —
   спецификация, но перечитай его против текущих миграций: агент мог не знать позднего файла.
2. **Прочитай, что уже есть.** Таблица или функция могла меняться в нескольких файлах —
   `grep -n "<имя>" supabase/migrations/*.sql`, действует последнее определение. Образцы стиля —
   `20261010120000_cloud_sync_client_ids.sql` (функции, повтор, замки) и
   `20260924180000_children_privacy_hardening_3.sql` (триггеры, псевдонимы).
3. **Свёртка (№87).** До первого наката на облачный Supabase миграции добавляются новыми
   файлами, перед шагом 7 сворачиваются в одну. Пока свёртки не было — только новый файл.

## Файл миграции

- Имя: `supabase/migrations/<ГГГГММДДччммсс>_<snake_case_смысл>.sql`, метка позже последней.
  **Существующие файлы не редактируются** — даже опечатку в комментарии.
- Шапка — блок комментария как в прежних: что было не так (с номером находки: `Р1`, `А6`,
  решение `№90`), что меняется, почему так, что сознательно не делается.
- Функции:
  - `SECURITY DEFINER` только когда нужно обойти RLS; тогда **всегда** `SET search_path = ''`
    и полные имена (`public.children`, `auth.uid()`);
  - доступ проверяется внутри функции от `auth.uid()`, а не по аргументу: `childId` из
    вызова — не проверка;
  - новая сигнатура старой функции — `DROP FUNCTION` старой и `CREATE` новой, не
    `CREATE OR REPLACE` (иначе перегрузка — две функции с одним именем); `CASCADE` не
    использовать;
  - права в конце файла: Supabase выдаёт `EXECUTE` anon и authenticated на каждую новую
    функцию. Внутренние и триггерные — `REVOKE ALL ... FROM PUBLIC, anon, authenticated`;
    вызываемые клиентом — `REVOKE ALL ... FROM PUBLIC, anon` (аноним без входа не вызывает
    ничего).
- Права `has_consent` не расширяются; `consent_active` — только `service_role`.
- Таблица: `ENABLE ROW LEVEL SECURITY` в том же файле; политики по отдельным действиям
  (`select` / `insert` / `update` / `delete`), с явным `TO authenticated`. Журналы
  (`consent_events`, `child_access_log`) — только дописывание: без политик `update` и
  `delete` для клиента.
- Данные о ребёнке минимальны: имя ребёнка в облако не уходит (№85), ABA — только на
  устройстве. Новая колонка с данными ребёнка — вопрос `child-privacy-compliance` до SQL.
- Коды ошибок — по таблице адаптера над `SyncProblemCode`
  (`talentia-mobile/src/services/local/sync.ts`): `22023` — устаревший текст / неверный
  аргумент (`outdated_text`), `23514` — время устройства (`device_clock`), `42501` — нет
  доступа (`no_access`; у `create_child` — `child_id_taken`), `23503` — ребёнка нет
  (`child_gone`), `22P02` / `23505` — плохие данные или id занят другим содержимым
  (`invalid_data`). Кода, которого нет в таблице (например, `54000` у `guardian_limits`),
  клиент не различит — повторит вечно. Новый код или новый смысл старого — правка таблицы и
  `SyncProblemCode` в том же изменении или строкой в REBUILD.md, «Отложено», «Адаптер Supabase».

## Тесты

Файл `supabase/tests/<тема>.test.mjs` — новый или дописать существующий по той же теме.
`tests/run.mjs` подхватывает каждый `*.test.mjs` сам; в `package.json` ничего не добавлять.

- Каркас — как в `cloud_sync_idempotency.test.mjs`: `runner()` и `group` / `check` / `finish`
  из `harness.mjs`, `actor(db)` для вызова от лица пользователя (`null` — аноним без входа,
  `{ id, anonymous: true }` — анонимный вход), `admin` — проверить, что записано на самом деле.
- Отказ проверяется **по конкретному SQLSTATE** (`fails(p, '42501')`): «упало по другой
  причине» — провал теста.
- Обязательные сценарии для всего, что касается ребёнка:
  1. владелец может то, что должен;
  2. **посторонний взрослый не видит и не меняет чужого ребёнка** (ни строкой, ни функцией,
     ни по известному id);
  3. аноним без входа и анонимный вход — отказ;
  4. взрослый с заявкой в ожидании или отклонённой — отказ; роль `specialist` политик не
     открывает;
  5. после отказа в базе ничего не записано (`adminCount`);
  6. сам блокер: сценарий, который был сломан, — теперь отклонён или исправлен.
- Прогон: `npm run test:db` из корня. Зелёный — все файлы, не только новый.
- PGlite — одно соединение: **гонки, `FOR UPDATE` между сессиями и PostgREST не
  проверяются.** Если правка о гонке или о том, что видит REST, — написать это в шапке
  теста и в отчёте: перед облаком нужна ветка Supabase (внешний скилл, шаг 7).

## Проверка и запись

1. Тесты пишет и прогоняет `qa-engineer`, если они больше пары сценариев или нужна проверка
   мутантами (убрать строку миграции → тест должен покраснеть).
2. Готовую миграцию проверяет агент зоны: `child-privacy-compliance` — всё о ребёнке,
   `backend-auditor` — схема. Блокер агента — исправить и показать ему снова.
3. Закрытую находку — в журнал скиллом `rebuild-log` (статус в AUDIT.md с файлом миграции
   и тестом, строка в «Истории»). Коммит — миграция и тест вместе.

## Отчёт пользователю

Файл миграции, что он меняет одной-двумя фразами, тесты (файл, число сценариев, итог
`test:db`), что PGlite не проверил, вердикт агента, хеш коммита.
